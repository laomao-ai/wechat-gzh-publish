## 为什么下面这些还不启用

内容方法类的东西，容易犯一个错：**把个人化的经验当成客观规律写进规则。**

正确做法是**只保留可验证的部分**——比如长度区间（有样本统计支撑）、事实红线（有因果）、AI 味信号（可观察）。个人化的语气偏好、特定的句式模板，都不该固化成规则。

## 附：调研发现的反模式（有据可查）

这些是定稿时要避开的坑：

**规则会随外部世界腐化**
`gzh-design-skill` Issue #13 —— 签名区把「点赞、在看、转发三连」写死，平台 UI 一改（实际已改成"点赞、转发、推荐"）就全错。

**错的约束比自由更危险**
Issue #20/#21 —— 主题库把"渐变背景"固化成设计规范，微信 Dark Mode 算法会 mix 成纯色，荧光笔"半高"退化成整块色块。维护者自己承认："上一版归因到 `overflow-x:auto`，那个诊断是错的"。

**维护者主动拒绝增量**
`gzh-design-skill` PR #10/#7/#9 全部 CLOSED，理由一致：
- 「新增科技钴蓝主题 → 维护收益较低」
- 「纯蓝开场和尾部区块偏重」
- 「API 上传草稿 → **一键直入草稿箱并不是刚性需求**」

第三条值得记着：我们的 `wechat_draft.py` 做的正是这件事。区别在于**我们有固定的运维约束**（IP 白名单 + 个人主体无发布权限），所以对我们是刚性的。

**业界解法是加脚本，不是加文字规则**
`gzh-design-skill` 的 `references/eval-cases.md` 用 checkbox 回归用例约束**触发行为**，而非输出质量——因为 description 一改就可能误触发，这是可确定测的。
